# Verba — Backend Architecture

> Local-first, open-source language learning with AI-generated curricula and a conversational tutor.
> This document describes the Python backend: data model, LLM provider layer, AI pipelines, and API surface.
> The clickable UI prototype lives in `index.html` and mirrors every flow described here.

## 1. Overview & principles

Verba is a Duolingo-style learning app that runs entirely on the user's machine. Three engines share one core:

1. **AI curriculum** — a CEFR-aligned tree (levels → units → missions → tasks) generated by a local LLM, stored in SQLite, and adapted to the learner's measured weaknesses. Any node can be regenerated.
2. **Task engine** — Duolingo-style exercises (multiple choice, translation, word order, fill-the-gap, listening, speaking) where every task is JSON produced under a strict schema and validated with Pydantic before it reaches the UI.
3. **Conversational tutor** — role-played scenarios with a persona calibrated to the learner's level. Every user reply passes through a **separate judge** that extracts structured errors, explains them, generates targeted drills, and feeds spaced repetition.

The product is not the curriculum. The product is the closed loop:

```
error → diagnosis → drill → SRS → adapted curriculum
```

Non-negotiable principles:

- **Local-first.** Zero cloud calls in the default configuration. All inference runs through local runtimes (LM Studio, Ollama, MLX, or HF Transformers as fallback).
- **Structured output or nothing.** Anything an LLM produces that drives logic must be valid JSON; failed generations are repaired and retried, never shown raw. Task payloads are additionally validated per kind; full JSON-Schema validation of judge/curriculum output is planned for v0.2.
- **The judge is not the tutor.** Different prompts, different system context, optionally different models. The tutor stays in character; the judge stays analytical.
- **One profile per machine.** No accounts, no sync, no telemetry. The SQLite file is the user's data.

Recommended models (all local, no account). **Provisional — under review:** newer, denser models exist and this selection will be revisited. Nothing in the code assumes these ids: roles resolve to whatever the local runtimes actually expose (`providers/base.py::resolve_roles`).

| Role | Model | Format | Size |
|---|---|---|---|
| Tutor persona | Qwen3-8B-Instruct | GGUF Q4_K_M | ~5.2 GB |

An 8B multilingual model is the sweet spot: strong English plus the meta-linguistic ability to *explain* errors. The generator role tolerates a 3B model; tasks are small, rigid JSON.

## 4. Data model

Single SQLite file at `verba.db`. SQLModel tables (abridged to the fields that matter):

```sql
-- Curriculum tree. One row per node; depth 0=level, 1=unit, 2=mission.
CREATE TABLE nodes (
  id          TEXT PRIMARY KEY,          -- ulid
  language    TEXT NOT NULL,             -- 'en' in v1
  kind        TEXT NOT NULL,             -- 'level' | 'unit' | 'mission'
  cefr        TEXT,                      -- 'A1'..'C2' (levels/units)
  title       TEXT NOT NULL,
  description TEXT,
  parent_id   TEXT REFERENCES nodes(id),
  position    INTEGER NOT NULL,          -- order within parent
  generated   INTEGER NOT NULL DEFAULT 1,-- 0 = hand-seeded skeleton
  created_at  TEXT NOT NULL,
  regen_count INTEGER NOT NULL DEFAULT 0
);

-- Generated exercises. One row per task; belongs to a mission.
CREATE TABLE tasks (
  id         TEXT PRIMARY KEY,
  mission_id TEXT NOT NULL REFERENCES nodes(id),
  kind       TEXT NOT NULL,              -- mc | translate | gap | order | listening | speaking
  payload    TEXT NOT NULL,              -- JSON, schema per kind (see §7.2)
  difficulty REAL NOT NULL DEFAULT 0.5,  -- 0..1, set by generator, tuned by performance
  created_at TEXT NOT NULL
);

-- Grading source of truth.
CREATE TABLE attempts (
  id         TEXT PRIMARY KEY,
  task_id    TEXT REFERENCES tasks(id),  -- NULL for tutor replies
  session_id TEXT,
  is_correct INTEGER NOT NULL,
  latency_ms INTEGER,
  answer     TEXT,                       -- what the learner produced
  created_at TEXT NOT NULL
);

-- Diagnosed errors: the learner's real profile, the product's core.
CREATE TABLE errors (
  id         TEXT PRIMARY KEY,
  category   TEXT NOT NULL,   -- grammar | articles | tense | word_choice | word_order | mechanics | speaking | listening
  wrong      TEXT NOT NULL,
  right      TEXT NOT NULL,
  explanation TEXT NOT NULL,  -- generated in the learner's UI language
  source     TEXT NOT NULL,  -- 'lesson' | 'tutor' | 'review'
  severity   INTEGER NOT NULL DEFAULT 1, -- 1 minor .. 3 core
  resolved   INTEGER NOT NULL DEFAULT 0, -- set when a later attempt proves mastery
  created_at TEXT NOT NULL
);

-- Spaced repetition (FSRS). One row per drillable item.
CREATE TABLE srs_cards (
  id           TEXT PRIMARY KEY,
  front        TEXT NOT NULL,
  back         TEXT NOT NULL,
  example      TEXT,
  source       TEXT NOT NULL,   -- 'seed' | 'error:<error_id>'
  stability    REAL NOT NULL DEFAULT 0,
  difficulty   REAL NOT NULL DEFAULT 5,
  due_at       TEXT NOT NULL,
  last_grade   TEXT,            -- again | hard | good | easy
  retired      INTEGER NOT NULL DEFAULT 0
);

-- Tutor conversations.
CREATE TABLE chat_sessions (
  id          TEXT PRIMARY KEY,
  language    TEXT NOT NULL,
  scenario    TEXT NOT NULL,     -- scenario id or free-form seed
  persona     TEXT NOT NULL,
  level       TEXT NOT NULL,     -- calibrated CEFR of the persona's English
  status      TEXT NOT NULL DEFAULT 'active',  -- active | done | abandoned
  created_at  TEXT NOT NULL
);
CREATE TABLE chat_messages (
  id          TEXT PRIMARY KEY,
  session_id  TEXT NOT NULL REFERENCES chat_sessions(id),
  role        TEXT NOT NULL,     -- tutor | user | system
  content     TEXT NOT NULL,
  diagnosis   TEXT,              -- JSON: judge output for user messages (see §7.3)
  created_at  TEXT NOT NULL
);

-- Progress & stats (drives the Stats screen).
CREATE TABLE daily_stats (
  day      TEXT PRIMARY KEY,     -- YYYY-MM-DD
  xp       INTEGER NOT NULL DEFAULT 0,
  missions INTEGER NOT NULL DEFAULT 0,
  errors   INTEGER NOT NULL DEFAULT 0
);
CREATE TABLE profile (
  key   TEXT PRIMARY KEY,        -- level, xp, streak, goal_target, theme, ui_lang, ...
  value TEXT NOT NULL
);

-- Detected runtimes and role assignment (mirrors the Models screen).
CREATE TABLE runtimes (
  id       TEXT PRIMARY KEY,     -- 'lmstudio' | 'ollama' | 'mlx' | 'hf'
  endpoint TEXT NOT NULL,
  status   TEXT NOT NULL,        -- 'detected' | 'missing'
  models   TEXT NOT NULL         -- JSON list [{id, fmt, size_bytes}]
);
CREATE TABLE role_assignments (
  role     TEXT PRIMARY KEY,     -- 'tutor' | 'judge' | 'generator' | 'stt' | 'tts'
  runtime  TEXT NOT NULL REFERENCES runtimes(id),
  model_id TEXT NOT NULL
);
```

Indexes: `tasks(mission_id)`, `attempts(task_id, created_at)`, `errors(category, resolved)`, `srs_cards(due_at) WHERE retired=0`, `chat_messages(session_id, created_at)`.

## 5. LLM provider layer

One abstract interface, four adapters. Everything above this layer is runtime-agnostic.

```python
class LLMProvider(Protocol):
    async def list_models(self) -> list[ModelInfo]: ...
    async def complete(
        self,
        messages: list[Message],
        *,
        model: str,
        json_schema: dict | None = None,   # structured output when supported
        temperature: float = 0.7,
        max_tokens: int = 1024,
    ) -> AsyncIterator[str]: ...           # token stream
```

| Adapter | Transport | Discovery | Structured output |
|---|---|---|---|
| `lmstudio` | OpenAI-compatible HTTP, `127.0.0.1:1234/v1` | `GET /v1/models` | `response_format: json_schema` |
| `ollama` | native HTTP, `127.0.0.1:11434` | `GET /api/tags` | `format: <json schema>` |
| `mlx` | oMLX (PrismML) or `mlx-lm serve`, OpenAI-compatible | `GET /v1/models` with Bearer auth from `~/.omlx/settings.json` | `response_format: json_schema` + pydantic repair |
| `hf_transformers` | in-process (last resort, milestone 2 stub) | local model cache scan | `outlines` grammar-constrained decoding |

The MLX adapter talks to oMLX (the default MLX runtime on macOS installs): it sends the local API key as Bearer auth, disables thinking mode on chat templates (`chat_template_kwargs.enable_thinking=false`, so Qwen-style models don't burn the token budget on invisible reasoning) and strips any leftover `<think>` span from the stream. Transient 404/502/503s from a freshly spawned server are retred with backoff.

**Runtime lifecycle** (oMLX, osusume pattern): at startup the backend probes the MLX endpoint; if nothing answers and a local oMLX install exists (CLI + models), it spawns `omlx serve` detached and refreshes the runtime discovery once the server responds. On shutdown only an app-owned server is killed (SIGTERM to its process group, 10 s grace, then SIGKILL + reaping); a server someone else started is left running. No oMLX install means plain degraded mode (opt out of the spawn entirely with `VERBA_LLM_SPAWN=0`).

**Discovery at startup** (mirrors the Models screen):

1. Probe `:1234` (LM Studio), `:11434` (Ollama) and the oMLX/MLX endpoint (`VERBA_MLX_ENDPOINT`, default `:8080/v1`). 800 ms for the first two, 4 s for oMLX — a busy server answers slowly, and a false miss would invite duplicate spawns.
2. Detected runtimes are stored in `runtimes`; their models enumerated.
3. Role assignment: auto-fill `role_assignments` by heuristic (largest known size → judge, next → tutor, smallest → generator; only Ollama reports sizes, so for OpenAI-compatible runtimes the discovery order decides), overridable by the user. Roles are resolved lazily per request, so switching a model in the UI takes effect immediately.
4. If nothing is detected, the app runs degraded: seeded demo curriculum, tutor disabled, download guidance shown with the right format per platform (GGUF for LM Studio/Ollama, MLX 4-bit on Apple Silicon).

**Generation pipeline** (every LLM call that must return JSON):

```
prompt ──► provider.complete(json_schema=S)
       ──► json.loads
       ──► must be a JSON object
       ├── valid   ──► done (field-level validation happens in the consumer:
       │                 tasks.validate_payload per kind, judge _norm_error)
       └── unparsable / not an object ──► repair prompt ──► retry (max 2)
                                             └── still invalid → 503 with reason
```

Never parse LLM output with hope: an unparsable reply triggers a repair retry, and every downstream consumer validates its fields (task payloads per kind with range/emptiness checks, judge errors normalized and category-clamped). Full JSON-Schema validation of judge/curriculum output is planned for v0.2.

## 6. API endpoints

All under `http://127.0.0.1:<port>/api`. JSON in/out unless noted. SSE endpoints stream `text/event-stream`.

| Method | Path | Purpose | Feeds prototype screen |
|---|---|---|---|
| `GET` | `/health` | status + version + db path | desktop shell health poll |
| `POST` | `/shutdown` | graceful stop (called by the shell on quit) | — |
| `GET` | `/profile` | level, xp, streak, goal, placement (read-only) | Path banner, Stats |
| `POST` | `/onboarding/placement` | score placement answers → level + initial unlocked set | Onboarding wizard |
| `POST` | `/onboarding/goal` | set daily goal target (the backend counts completed missions toward it) | Onboarding wizard |
| `GET` | `/path` | curriculum tree + completion status + current mission | Path |
| `POST` | `/missions/{id}/start` | get (or lazily generate) the mission's task list | Lesson player |
| `POST` | `/attempts` | submit a graded task answer → verdict + diagnosis | Lesson player |
| `POST` | `/missions/{id}/complete` | finalize mission: XP (scored from the recorded attempts), unlock next, errors recorded | Mission complete |
| `POST` | `/path/units/{id}/generate` | regenerate/extend a unit with the generator model | "Generate with AI" |
| `GET` | `/chat/scenarios` | available tutor scenarios | Tutor |
| `POST` | `/chat/sessions` | open a scenario session (persona + level) | Tutor |
| `GET` | `/chat/sessions/{id}/stream` | **SSE**: tutor tokens, then judge diagnosis event | Tutor |
| `POST` | `/chat/sessions/{id}/messages` | send user reply; triggers judge → diagnosis | Tutor |
| `POST` | `/chat/sessions/{id}/finish` | close scenario: summary + errors → Review | Tutor summary |
| `GET` | `/review/queue` | due SRS cards (FSRS) | Review |
| `POST` | `/review/grade` | grade a card (again/hard/good/easy) → new due date | Review |
| `POST` | `/review/generate` | generate extra drill cards from weak spots | "Generate extra drills" |
| `GET` | `/stats/overview` | xp, streak, accuracy, missions, totals | Stats |
| `GET` | `/stats/daily?days=14` | per-day xp/missions/errors | Stats chart |
| `GET` | `/stats/errors` | error counts by category | Stats / weak spots |
| `GET` | `/stats/library` | missions in library, SRS cards total/retired | Stats |
| `GET` | `/stats/profile-keys` | raw profile key/value pairs | internal |
| `GET` | `/runtimes` | detected runtimes + models + current role assignment | Models |
| `POST` | `/runtimes/scan` | re-probe endpoints | Models |
| `PUT` | `/roles` | assign model per role | Models |

Roles are read from `GET /runtimes` (`roles` key); there is no separate `GET /roles`. Theme/UI preferences stay client-side for v0.1 (no `/settings` endpoint).

**SSE contract for the tutor stream** (one connection per session):

```
event: token        data: {"delta": "Good "}          # persona tokens
event: message_end  data: {}                          # tutor turn done
event: diagnosis    data: {"score", "errors", "reply_coach"}   # after a user message (§7.3)
event: done         data: {"status": "complete"}      # or {"status": "error"} after event: error
```

The tutor streams first (fast, small model is fine), the judge runs as a second call. Both land through the same provider layer; the UI shows the diagnosis card as soon as `diagnosis` fires — matching the prototype's chat flow.

## 7. AI pipelines

### 7.1 Curriculum generation

Generated per node, cached in `nodes`/`tasks`. The generator receives: target CEFR level, unit topic, the learner's error profile summary (top categories + example errors), and vocabulary already covered. It must return a JSON tree of missions; each mission is expanded into tasks only when first opened (keeps generation fast and saves tokens).

```
Input  : level=A2, unit="Out & about", profile={tense: 4, word_choice: 2}, known_vocab=[...]
Output : [{ "title": "Last weekend", "objective": "...", "target_categories": ["tense"] }, ...]
Schema : CURRICULUM_SCHEMA (declared to the model, enforced inline: ≤ 5 missions, titles ≤ 40 chars, no duplicate mission titles in unit)
```

Regeneration replaces a node's subtree and bumps `regen_count`; completed missions are never silently deleted.

### 7.2 Task generation

One JSON schema per `kind`. The generator prompt binds: mission objective, learner level, weak categories to target, and 3–5 example tasks from the prototype as few-shot anchors. Payload contracts:

```jsonc
// kind: "mc" and "gap" (same shape)
{ "prompt": "Good evening. Do you have a reservation ___ the name Rossi?",
  "choices": ["by", "under", "at", "with"], "answer": 1,
  "why": "Bookings are made under a name." }

// kind: "translate"
{ "prompt": "Translate: “Ho prenotato una doppia per tre notti.”",
  "accepted": ["i booked a double room for three nights"],
  "answerText": "I booked a double room for three nights.",
  "why": "..." }

// kind: "order"
{ "prompt": "Build the question:",
  "words": ["Have", "you", "ever", "stayed", "with", "us", "before?"],
  "why": "Present perfect question: Have + subject + ever + past participle." }

// kind: "listening"
{ "say": "Your room is on the third floor.", "accepted": ["..."], "why": "..." }

// kind: "speaking"
{ "say": "I'd like a double room for three nights, please." }
```

Rules enforced by validation: `answer` must index `choices`; `order.words` must form one grammatical sentence; translation `accepted` uses normalized lowercase; distractors must be plausible, not absurd. Bad generations get repaired, not shipped.

In v1, the six hand-authored task sets in the prototype ship as seed content so the app works before any generation; generation extends and personalizes from there.

### 7.3 The judge (the core of the product)

Separate prompt, separate model slot, no persona. Input: the last tutor turn, the learner's reply, the learner's level, and the running scenario context. Output contract:

```jsonc
{
  "score": 86,                                   // 0..100
  "errors": [
    {
      "category": "tense",
      "wrong": "I am here since 2019",
      "right": "I've been here since 2019",
      "explanation": "An action continuing until now takes the present perfect.",
      "severity": 2
    }
  ],
  "reply_coach": "Good try — quick fix: use 'I've been here since…'.",
  "suggested_drill": { "front": "since vs for", "back": "since + start point, for + duration", "example": "I've lived here since 2019." }
}
```

- The prototype's 15+ deterministic rules ("I am agree", "informations", "didn't went", "I have 25 years", "a/an"…) become a **fast pre-pass**: cheap, instant, catches the highest-frequency calques. The LLM judge runs on everything and merges with the pre-pass — deterministic findings filter LLM false positives, LLM findings catch what regex never will.
- `suggested_drill` seeds SRS directly (deduplicated by front, `source='error:llm'`). `reply_coach` is produced (required by the judge schema) but not yet consumed by the tutor — candidate for v0.2.
- Every error row gets `source='tutor'` and flows into Review + the curriculum's `target_errors`.

### 7.4 Adaptive path

`GET /path` ranks candidate missions by: prerequisite order (fixed), overlap with unresolved error categories (up-weight), and time since the category was last drilled. The "current mission" pointer follows the learner's placement plus this ranking — this is what makes the curriculum *generated and adapted* rather than a fixed ladder.

## 8. Scoring, FSRS, error taxonomy

- **Task scoring**: deterministic per kind (exact/normalized match for translate/listening/speaking, index match for mc/gap, sequence match for order). Speaking uses word-level alignment; accept ≥ 80 % of target words (prototype parity; real pronunciation scoring arrives with whisper.cpp alignment in v2).
- **Tutor scoring**: judge `score` (0–100), feeding the scenario summary.
- **XP**: `20 + accuracy/5` per mission (prototype formula, keep for v1). XP writes to `daily_stats` and `profile`.
- **FSRS** for `srs_cards`: default parameters, four grades (again/hard/good/easy) mapping to rating 1–4. Grading a non-retired card increments `daily_stats` toward the goal. `source='error:<id>'` cards retire when stability crosses the threshold, which also marks the originating error `resolved` — closing the loop into the adaptive path.
- **Error taxonomy** (fixed enum): `grammar, articles, tense, word_choice, word_order, mechanics, speaking, listening`. UI categories in the prototype map onto this list; the Stats "errors by category" endpoint aggregates over it.

## 9. Voice

- **STT** — whisper.cpp, `base.en`/`small.en` quantized, loaded in-process. Endpoints: `POST /voice/transcribe` (audio blob → text). Used by speaking tasks and (v2) tutor voice input. The prototype uses the browser's Web Speech API and says so; the backend replaces it with a fully local path.
- **TTS** — Piper, one `en_US` voice. `POST /voice/tts` → wav. Replaces the browser's `speechSynthesis` for listening tasks and tutor speech.
- **Pronunciation scoring** (v2): forced alignment of the transcript against the target sentence (word-level timestamps from whisper) → per-word accuracy, beyond the prototype's word-recognition-only check.
